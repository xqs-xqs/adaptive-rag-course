# REFACTOR_PLAN — adaptive-rag-course 生产化重构总计划

> 本文件是整个重构的**唯一权威状态源**。任何会话（人类或 Claude Code）恢复上下文，都从这里开始读。

## 1. 使命

把一个 vibe coding 产出的 RAG demo 改造成可以在国内大厂后端面试中经得起追问的生产级项目。
**算法层（混合检索 / RRF / 意图路由 / parent-child 分块 / 重排）基本保留不动**，重构对象是工程层：结构、配置、容错、缓存、观测、索引生命周期、部署。

## 2. 非目标（明确不做，防止过度工程）

- 不引入 Kafka / 消息队列、K8s、微服务拆分、服务网格、DI 框架
- 不新增检索算法（HyDE、GraphRAG、query expansion 等一律不加）
- 不迁移语言（保持 Python），不更换 Web 框架
- 不追求覆盖率数字、镜像大小等易被刷指标的虚荣目标

判断标准：每引入一样东西，必须能回答「为什么需要、不加会怎样、什么量级下才真正需要」。答不出 → 不加。

## 3. 全局不变量（每个阶段结束时都必须成立）

| 编号 | 不变量 | 验证方式 |
|---|---|---|
| I1 | 检索侧评测指标（Hit Rate / Recall / MRR）相对基线回退 ≤ 0.01 | 对比 `docs/baseline/` 基线 JSON 与本阶段评测 JSON |
| I2 | 生成侧指标（Faithfulness 等，LLM 评审有随机性）只记录、不做门禁 | 写入阶段报告即可 |
| I3 | 已有测试全绿 | `pytest -q`（Phase 2 起） |
| I4 | 冒烟测试通过：服务能启动并回答 1 个标准问题 | `bash scripts/smoke.sh` |
| I5 | 对外 API 契约（路径、请求/响应结构、SSE 事件格式）不变，除非当前阶段规格明确声明变更 | 契约测试（Phase 2 起）+ 人工确认 |

> **阈值校准说明**：I1 的 0.01 是初始值。Phase 0 会把基线评测跑两遍，测出自然方差后校准此阈值（记录在下方第 7 节）。校准前该阈值视为草案。

## 5. 人机协作流程（每个阶段固定三步，不可跳过）

1. **讲解课**（Claude.ai 对话）：人类带着当前代码上 Claude.ai，先学懂本阶段概念——解决什么问题、没有它线上会怎么死、最小心智模型。
2. **执行**（Claude Code）：人类说「开始阶段 N」→ Claude Code 走会话启动协议（见 CLAUDE.md）→ 假设核对 → 执行计划获批 → 实施 → 跑验收 → 写报告 → 停。
3. **审查课**（Claude.ai 对话）：人类带 diff 和阶段报告回 Claude.ai，逐块 review：验收是否真达成、有没有夹带私货、哪几处是面试考点。人类确认后自己合并 PR。

**阶段门 = 人类合并 PR。** Claude Code 无权宣布阶段完成，也无权开始下一阶段。

## 8. 已知风险与假设

- 本计划由 Claude（Claude.ai）基于 2026 年 4 月对代码库的完整阅读写成。**仓库当前状态可能已偏离**——因此每个阶段规格的第 0 节都是强制的前置假设核对，偏差即停。
- 评测依赖 DashScope 真实 API：有费用、有速率限制、生成侧指标有随机性。对策：检索侧指标做门禁、生成侧只记录；CI 中评测为手动触发（Phase 2）。
- BM25 索引在内存中启动时构建（待 Phase 0 确认）：Phase 6 前每次重启都全量重建，这是已知且接受的现状。
